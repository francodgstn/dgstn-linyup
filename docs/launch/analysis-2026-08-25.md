## A. BLOCKS A CUSTOMER

### A2 (remainder). The DPA and privacy policy still say "Switzerland" for compute `[V]`
**What:** the compute move is done — prod web + operator console now run in
`europe-west4`. The DOCUMENTS were never amended: `apps/landing/src/pages/dpa.md:89`
puts Hosting in the "Switzerland (europe-west6, Zurich)" row and `:109` states
"Application data is processed in Switzerland"; `privacy.md:80,85` repeat it.
**Breaks:** europe-west4 is the **Netherlands**, not Switzerland. The DPA is a
contract a studio signs and it is false on a point counsel will check —
discoverable with `dig`. Storage genuinely is in Zurich; compute is now EU but
not Swiss, which is a better story than before and still not the one on the page.
**Do:** amend the sub-processor table + the "processed in" wording to say storage
in Zurich (europe-west6), compute in the EU (europe-west4). Trivial edit; it is
listed here because it is the half that makes the other half honest.
**Effort:** trivial.

### A3. No off-project backup, no restore runbook, no rehearsal `[V]`
**What:** two lanes **disagreed on severity** (ops-deploy: high; ops-data-safety:
low, on the strength of project soft-delete + `DELETE_PROTECTION_ENABLED`). Facts
both agree on: prod has PITR (7d window), delete protection, and a daily managed
schedule at the 14-week max with 7 READY backups — **all inside `linyup-prod`**.
`gcloud storage buckets list` shows no export bucket in any project.
`infra/modules/firestore/main.tf:46-51` says the off-project copy "is tracked
separately" — it is tracked nowhere. `docs/launch/restore-runbook.md` **does not
exist**, and `.claude/agents/ops-agent/AGENT.md:170-172` instructs the operator to
refuse to improvise without it (and at `:167` misnames managed backups as
"scheduled exports").
**Breaks:** "We have backups" is verified; "we can restore" is untested. Recovery
is contingent on `linyup-prod` continuing to exist (billing lapse, compromised
owner, Google-side action). In an incident the one doc an operator opens
disclaims itself.
**Do:** (a) Write `docs/launch/restore-runbook.md` covering PITR
read-at-timestamp, managed-backup restore into a scratch DB (**answer: how do you
get it back into `(default)` behind delete protection, and what do
Functions/App Hosting point at meanwhile**), and Storage object restore.
(b) Rehearse one restore, record elapsed time. (c) Add a scheduled
`gcloud firestore export` to a bucket in a **different** project, or delete the
comment claiming coverage and record the accepted risk. (d) Fix `AGENT.md:167`.
**Effort:** medium. **This is now the largest open A-item.**

   passwordless sign-in is not broken.
5. **No gen1 functions remain** anywhere in `packages/functions/src` — the
   brevo-api-key/appspot-SA failure class is closed (PR #99).
6. **No secrets are committed.** The tracked env files hold only non-secret
   config; everything real goes through Secret Manager.

   `mail_suppressions`, `platform_notices` + recipients, `signup_allowlist`/

9. **`purge-team.ts` and `reset-sandbox-db.ts` are exemplary** — hardcoded/

## What is still unverified

**Live-project unknowns.**
- **Which Identity Platform sign-in providers are actually enabled** — the
  identitytoolkit admin API returned 403 for ADC on all three. Console →
  Authentication → Sign-in method, 60 seconds, gates two of four ways into the
  product.
- **Whether the alert notification channel is verified** — `verificationStatus`
  came back empty. An unverified channel is created, enabled, and delivers
  nothing. Only honest test: induce a failure and confirm mail arrives.
- **Whether App Hosting auto-rollout is genuinely off** on prod/sandbox — the
  setting is exposed by neither CLI nor REST API. `infra/README.md` §6's empirical
  recipe is the only test.
- **Which commit each environment's *web* app is serving** (D23).
- **What is actually in Secret Manager per project**, versus what the code asks
  for by name.
- **Whether the GitHub `staging` environment has required reviewers.** If it has
  none, the destructive reseed is one dispatch + one checkbox from anyone with
  write access. Prod and sandbox are known to require approval.

**Data-shape unknowns.**
- **Whether either v0.8.0 backfill has ever been run, anywhere** — no ledger, no
  marker document (D8). `backfill-booking-joined-at` is idempotent and
  dry-run-by-default, so re-running it against staging is cheaper than
  establishing whether it ran.
- **How many production tenants have `source: 'aggregator'` subscription types** —
  A7 was ranked on mechanism, not on a victim count. The dry-run before any
  `--apply` of `backfill-public-subscription-types.ts` still has to be read by a
  human; that script's `--apply` can publish a studio's partner deals.
- **Snapshot inventories.** Claims come from binary grep over LevelDB exports:
  reliable for proving **absence**, useless for counting documents. CLAUDE.md's
  "28 teams" figure for `snapshots/all` is unconfirmed.
- **`pnpm typecheck:seeds` proves less than it looks.** Seeders write untyped
  literals into `db.collection().set({...})`, accepted as `DocumentData` — so
  neither an extra field nor a missing required one produces a compile error.
